# Review

- [fixed] correctness: the sender ID parser accepted any printable character for up to 8 bytes. A header quoted in a CSV field or followed by a delimiter (`"...-WAAA/FM",ok`, `...-WAAA/FM,2026-03-02`, `...-WAAA/FM</td>`) gave senders like `WAAA/FM"` or `WAAA/FM,`. These never matched `--source`/`--station`, so every week showed a false "no test received" PROBLEM (src/same.rs:126) -> the sender field now accepts only letters, digits, `/`, space, `.`, `_`. Test: `same::tests::sender_stops_at_csv_or_quote_delimiters`.
- [fixed] correctness: quoted-printable decoding only ran when the *top-level* e-mail headers declared it. Saved multipart e-mails declare the encoding on the MIME part, so a soft line break inside a header (`...WAAA/F=\nM -`) was left in place. The header was then lost or mis-parsed (src/extract.rs:115) -> any `Content-Transfer-Encoding: quoted-printable` line in the record now turns on decoding. Test: `extract::tests::multipart_quoted_printable_part_is_decoded`.
- [fixed] correctness: relay delay was rounded down to whole minutes, so an RMT relayed after 60 min 40 s showed "60 min" and passed the 60-minute rule (src/review.rs:274) -> the delay now rounds up, so anything over 60:00 fails. Test: `relay_just_over_60_minutes_is_late` (tests/cli.rs).
- [fixed] correctness: ISO 8601 timestamps with a colon zone offset (`2026-03-02T10:00:05-06:00`, a common export format) were not recognised. Those entries silently fell back to the header's issue time, contrary to the README's "zone suffixes are ignored" (src/time.rs:156) -> a trailing `+HH:MM`/`-HH:MM`/`+HHMM` is now stripped from time tokens. Test: added cases in `time::tests::timestamps_in_common_styles`.
- [fixed] correctness/honesty: when a time had to come from the SAME header, the tool silently used `--utc-offset` 0 (UTC) by default. For a US station that puts the time 4–10 hours off, so a Saturday-evening RWT can land in the next week and flip a week's verdict. The fallback also runs for timestamps more than 36 h from the header time, not only for undated logs (src/main.rs:load) -> the tool now prints a stderr warning, with a count, when header times were used without `--utc-offset`. The README option table says so. Test: `header_time_without_utc_offset_warns` (tests/cli.rs).
- [unfixed] rules: in a week with a received RMT, a source that sent nothing is only reported as a note, not as a problem (src/review.rs, source loop). This is a deliberate, documented policy, and IPAWS RWT behaviour in RMT weeks varies. Making it a problem could produce false alarms. I left it as documented.
- [unfixed] limitation: a log that prints the timestamp *after* each header gets the previous record's time. This is documented ("nearest date and time written before it"). Fixing it needs a format-detection feature, not a bug fix.

Harm review: the tool reads only the station's own logs. It collects no personal data, makes no network calls and profiles no one. Its defaults (no `--source` or `--station`) produce a weaker review and say so in the notes, so nothing is hidden. Completeness: `report`, `senders`, `decode`, CSV output and exit codes all work end to end on the three fixture styles, as `PROBLEM.md` describes. Performance: 20,000 events in 2 s (release build), so a month of logs is instant. Install URLs already match `$FORGE_REPO_BASE`.

Summary: the project is complete and does what PROBLEM.md promises. Its core logic (SAME parsing, per-source weekly table, RMT relay check) is sound. The bugs I found were all on messy real-world input and produced wrong results without any warning: senders polluted by CSV quotes or commas (false "missing source" problems), multipart quoted-printable e-mails whose headers were lost, ISO timestamps with zone offsets that were not recognised, a 60-minute check that let up to 60:59 pass, and a silent UTC default that could move events into the wrong week. Each has a regression test that failed before its fix. All gates pass: fmt, clippy -D warnings, 30 tests, audit. The verdict stays `build`.
